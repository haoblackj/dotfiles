# Report

## これは何のためか

長いセッションの本文を読む負担を減らす。

そのセッションで何をやったかと、リーダーが聞いたことへの答えを、日本語の HTML1枚にまとめて Artifact へ publish し、URL を返す。
リーダーはチャットを遡る代わりにそれを読む。

## 手順

1. 対象の範囲を決める。既定はセッション全体。リーダーが範囲を添えていればそれに従う。
2. `artifact-design` スキルを読む。Artifact を作る前の必須手順。
3. HTML を書く。書き出し先はこのセッションのスクラッチパッドディレクトリ。ファイル名は `report-YYYYMMDD-HHMM-<slug>.html`。`<slug>` は主題を表す英小文字とハイフンだけの短い語。
4. `Artifact` ツールで publish する。`favicon` を指定する。
5. 返った URL を最終応答に書く。publish すると既定でブラウザが開くが、あとからターミナルの履歴で辿れるようにするため URL も残す。

呼ばれるたびに新しいファイル名にする。同じセッションで前に出したレポートは残す。

publish が失敗したら、その場で試し直さない。
ローカルのファイルパスを最終応答に書いて止める。

## レポートの構成

必須が3つ、任意が3つ。

**このセッションの主題（必須）。** 1文か2文。何を頼まれ、何をしているか。

**やったこと（必須）。** 時系列。変更したファイルと、変更した理由。読む人がコードを開かずに何が起きたか追える粒度にする。

**検証の結果（必須）。** 走らせたコマンドと、出力の要点。走らせていないなら走らせていないと書く。

**決めたことと、確認したこととその答え（任意）。** リーダーに聞いた内容と、返ってきた答え。設計上の判断と、その理由。

**図解（任意）。** 構造や流れが言葉より図で早いときだけ。mermaid か inline SVG。無理に入れない。

**未了と次の一手（任意）。** まだ終わっていないこと。次に何をするか。

任意の節は、該当する内容が無ければ節ごと落とす。
空の見出しを置いて中身を埋めさせない。

検証の結果の節を「検証済み」の一言で埋めない。
何を走らせて何が返ったかを書く欄である。

## 書くときの縛り

日本語で書く。

セッションに無いことを補完しない。
走らせていないコマンドの結果を書かない。
確認していないファイルの中身を書かない。

リーダーの発言を引くときは、言ったとおりに写す。
要約するなら要約と分かる形にする。

レポートを作るために新しく調査をしない。
セッションに既にある材料だけで書く。足りない部分は足りないと書く。
調査を始めると、読む量を減らすために使ったトークンで文脈を汚すことになる。

コンテキストの圧縮が起きたセッションでは、そのことをレポートに書く。
圧縮で落ちた範囲は説明できないので、完全な記録と誤解させない。

HTML は自己完結させる。外部ホストの CSS、スクリプト、画像に依存しない。
明暗どちらのテーマでも読める配色にする。

## やらないこと

**改善提案を書かない。** ハーネスやコードの改善案はこのレポートの担当ではない。
提案まで書くと、その場しのぎの修正が積み上がる。

**振り返りを記録しない。** 記録は別の仕組みが持つ。

**作業リポジトリへ書かない。** HTML はスクラッチパッドの外へ出さず、コミットもしない。

**サブエージェントへ逃がさない。** レポートはこのセッションの中で書く。
隔離自体は成立するが、いまのコンテキスト長では継承の費用に見合わない。

**`visual-html-renderer` を使わない。** HTML は自分で書いて `Artifact` へ渡す。
あちらは document-model の組み立てから render、validate、preview まで多段の CLI を通す作りで、
コメントの往復を伴うレビュー文書向け。読み捨てのレポート1枚には手順もトークンも重い。
