# Decision Required

## これは何のためのスキルか

プラン実行を止めた事項をリーダーへ提示するときの書式を定める。

書式は [MADR 4.0.0](https://adr.github.io/madr/) のミニマルテンプレート（Context and
Problem Statement、Considered Options、Decision Outcome）に `Pros and Cons of the
Options` を足したもの。`Status: proposed` で提案し、受理とともに `accepted` へ変える形は
ADR の標準的な運用で、[AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)
にも定義されている。独自の型ではない。

**止まる理由そのものはこのスキルが定めない。**既存の規定をそのまま使う。
このスキルが定めるのは、止まったあとどう聞くかだけである。

## 発行条件

### 使うとき

条件は2つを同時に満たすこと。

1. 止まる理由に当たる
2. 複数の妥当な案があって、どれを選ぶかで後続の作業が変わる

**片方だけでは使わない。**

止まる理由は既存の規定にある。superpowers の4つ（不可逆または破壊的な操作、
セキュリティに関わる操作、ワークツリーの外への副作用で規範が先に確認を求めるもの、
どの道を選んでも推測になるほど壊れたプラン）と、グローバル `CLAUDE.md` が確認を求める事項
（スコープを超える変更、本番データへの書き込みや削除、プロジェクトの依存への追加、
どのブランチに何を残すか消すか）である。

### 使わないとき

**実装者から `BLOCKED` が上がってきたこと自体は理由にならない。**

`implementer-prompt.md` は「複数の妥当な案があるアーキテクチャ判断」を上申の条件に
挙げているが、それは止まる理由ではない。superpowers は「衝突、曖昧さ、プランの欠陥は
統制側が裁定する」と定めている。条件に当たらなければ `Ruling:` を書いて進む。
実装者からの上申の大半はここで終わる。

**「自分で裁定できるか」を主観で判定しない。**判断に自信が無いことは理由にならない。
主観に委ねると、裁定して進むという既定が骨抜きになる。

**可否を確認するだけの事項は DR にしない。**「本番データへ書いてよいか」「プロジェクトの依存を
足してよいか」「マージしてよいか」は、選ぶ判断ではなく可否の確認である。グローバル
`CLAUDE.md` の「指示範囲の厳守」に当たる事項として、1行で確認すればよい。

可否の確認をこの型へ押し込むと、`Considered Options` に「B: やらない」という埋め草が
毎回入り、`Pros and Cons` がその埋め草の利点欠点を書くことになる。型が空回りするだけで、
判断材料は1行の確認より増えない。

境界の例。

| 事項 | 扱い |
|---|---|
| プロジェクトの依存を1つ足してよいか | 1行の確認 |
| プロジェクトの依存の候補が2つあってどちらも要件を満たす | DR |
| ブランチを消してよいか | 1行の確認 |
| どのブランチへ変更を残すかで後続のタスクの作業先が変わる | DR |
| プランどおりに書くと動かず、代替が1つに定まる | `Ruling:` |
| 代替が複数あるが、止まる理由に当たらない | `Ruling:` |

## 書式

```markdown
## DR-001: <決めることを一行で>

- Status: proposed

### Context and Problem Statement

何が起きていて、なぜ統制側では決められないのか。
実測した事実があれば添える。

### Considered Options

- A: <案>
- B: <案>

### Decision Outcome

推奨は A。<理由を一文か二文で>

### Pros and Cons of the Options

**A: <案>**

- Good, because <利点>
- Bad, because <欠点>

**B: <案>**

- Good, because <利点>
- Bad, because <欠点>
```

節名は英語のまま使う。MADR の型をそのまま当てていることが見て分かるようにするため。
節の中身は日本語で書く。

選択肢は2つか3つまで。4つ以上並ぶときは問題の切り分けが足りていないので、DR を分ける。

番号はプラン単位の連番で `DR-001` から始める。プランをまたいだ通し番号にはしない。
作業場が消えると採番の根拠が失われるため。

## 提示のしかた

**全文を出す。**要約すると、判断材料を揃えるという目的が消える。

複数の DR が同時に立つ場合は、番号の順にすべて出す。1つずつ出して回答を待つと、
往復が DR の数だけ増える。

DR を出したら、その判断に依存するタスクは進めない。依存しないタスクがあれば進めてよい。
進めた場合は何を進めたかを回答時に添える。

## 記録

**チャットへ出すのと同時に `progress.md` へ追記する**（`Status: proposed` のまま）。
回答を待ってからまとめて書かない。`progress.md` は superpowers が復旧の地図と
位置づけているファイルで、統制セッションが落ちた場合、書いていない DR は提示したこと自体が
失われる。

回答を受けたら `Decision Outcome` を採択された案へ書き換え、`Status` を `accepted` にする。

推奨と違う案が採られたときは、発行時の推奨を括弧で残す。

```markdown
### Decision Outcome

採択は B。<リーダーが理由を述べていれば添える>（発行時の推奨は A）
```

**リーダーの回答を写す欄を別に設けない。**`Decision` のような節を足して推奨と採択を
並べて残すと、台帳へ移ったあとに読む側が、どちらが実際に採られた案かを取り違える。
MADR では `Decision Outcome` が採択された案を持つ節である。

どの案も採らずに別の指示が出た場合は、その内容を `Decision Outcome` へ書いて
`accepted` にする。`rejected` は使わない。提案そのものが退けられる場面が、
この用途では選択肢の入れ替えと区別できないため。

DR は既存の `Ruling:` と同じファイルへ時系列で混ぜて並べる。どちらも「その時点で何が
決まったか」の記録で、読むときは時系列で追うため。`Ruling:` は統制側が裁定したもの、
`DR-NNN` はリーダーが裁定したもの、という区別は行頭の形で付く。

作業が終わったら、既存の手順どおり `docs/superpowers/ledgers/<プラン名>/` へ移す。

**`superpowers:executing-plans` でインライン実行しているときは `progress.md` が存在しない。**
その実行モードでは `.superpowers/sdd/` の作業場そのものが作られない。このときは DR を
プラン文書の該当タスクの直下へ追記する。プラン文書は追跡対象なので、コミットで残る。
作業場が無いことを理由に記録を省かない。
