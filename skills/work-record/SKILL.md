# 作業記録

作業記録は、判断と進行状態の正本。
書くのも直すのも Claude で、リーダーは書かない。
数週間ぶりに戻ったリーダーが、これだけ読めば、何のために何をしていて、どんな判断を経て今に至り、次に何が起きるかを分かるように書く。
時系列の作業日誌にしない。今の姿を節ごとに書き直し、経緯は「判断の経緯」に判断ごとに残す。

## 置き場

- 作業するリポジトリの `docs/work/<作業名>.md`。作業名は英小文字とハイフンで短く。
- 作業のブランチにコミットし、区切りごとに push する。push しないと ChatGPT からも、引き継ぎ先からも読めない。
- 公開リポジトリには、非公開の事情（他の非公開リポジトリの中身、個人の情報、秘密）を書かない。書く必要がある作業の記録は、その作業の非公開リポジトリに置く。
- 一つの作業に記録は一つ。同じ作業の記録を別の場所（issue のコメント、ダッシュボード、memory、引き継ぎのファイル）に書き写さない。そちらには記録へのリンクだけを置く。

## 書式

````markdown
---
title: <リーダーが読んで分かる作業の名前>
status: active   # active（進めている）、waiting（リーダーの答え待ち）、done（済み）、dropped（やめた）
wish: <prts の望みの ID>   # prts に望みがあるときだけ
---

## 目的
<リーダーが実現したいこと。`prts quote` が成功した依頼の原文を引用で置き、Claude の言い直しは別の行に「要するに」と書く>

## いまの方針
<今有効な要求と、採っている進め方を数行で。判断の経緯の「有効」なものと食い違わないように>

## 判明した事実
- <事実>（根拠: コミット、ファイル、URL、測った値）

## 判断の経緯
### <YYYY-MM-DD> 採用: <決めたこと>
- 出どころ: 端末からの入力（<会話>、<時刻>） / Claude の判断
> 「<原文>」（端末からの入力、<会話>、<時刻>）   # prts quote が成功したときだけ
- 理由: <なぜそうしたか。リーダーが理由を言っていなければ「理由の提示なし」>
- 状態: 有効

### <YYYY-MM-DD> 棄却: <採らなかった案>
- 理由: <なぜ採らなかったか>
- 状態: 有効

### <YYYY-MM-DD> 変更: <新しい決定>
- 置き換えたもの: <古い判断の見出し>
- 理由: <何が新しく分かったか、誰が変えたか>
- 状態: 有効

## いまの作業
<いま何をしているか。なぜそれを今しているか（どの判断や事実から来たか）>

## 済んだこと
- <済んだこと>（コミットや PR へのリンク）

## 残っていること
- <残り>

## 次に Claude がすること
- <次の一手。引き継ぎ先がこれだけ読んで始められる具体さで>

## リーダーに決めてほしいこと
- <問い>。Claude の案: <推奨と理由、トレードオフ>。答えで何が変わるか: <...>
<無ければ「なし」>

## 参照
- <issue、PR、設計書（superpowers の設計と計画）、関係するコミット>
````

## 言葉の区別

- `>` で始まる行は、`prts quote "<文の一部>"` が成功した端末からの入力の原文だけ。出典（会話、時刻）と「端末からの入力」を添える。
- 会話の記録では、リーダーが打った文と、Herdr などで別の Claude やスクリプトが打ち込んだ文が同じ形で残る。`prts quote` は端末からの入力の原文が記録にあることだけを確かめ、発言者は確定しない。引用に発言者をリーダーと書かない。
- PRTS の画面は、`>` の行が `prts quote` で覚えた引用と一致すれば「端末からの入力の原文」、しなければ「原文未確認」と添えて出す。
- `prts quote` が成功しない（記録に無い、端末からの入力でない、引用の位置にある、短すぎる）文は、引用符を付けずに「要約（原文未確認）: ...」と書き、決定の根拠にしない。
- Claude の解釈、Claude の案、リーダーが決めたことを混ぜない。Claude の案はリーダーの答えが出るまで「リーダーに決めてほしいこと」に置き、判断の経緯に「採用」として書かない。
- 技術の選択（どう作るか、どう試すか）は Claude が決めてよい。そのときは「出どころ: Claude の判断」と書き、理由を書く。

## 記録と、いまの指示

- 作業記録は過去の判断の記録で、いまのリーダーの指示を覆す根拠にしない。
- 優先の順: 安全と権限の決まり（指示範囲の厳守、本番データの保護、GitHub を含む外への書き込みの制限、環境の境界（WSL/Windows）、chezmoi の扱い、破壊的な操作）、いまの会話でのリーダーの指示、作業記録の「有効」な判断（出どころが端末からの入力の物）、CLAUDE.md の一般の決まり、作業記録のうち Claude の技術の判断、そのほか（memory、issue、圧縮の要約）。
- 出どころの分類は、記録と引用での扱いだけを決め、いまの会話で何に従うかは変えない。「出どころ: 端末からの入力」の判断は、端末から打たれた文に基づくことを示すだけで、リーダーが決めたと確かめた物ではない（別の Claude やスクリプトが打ち込んだ文も同じ形で残る）。
- いまの指示が記録の判断と食い違えば、指示に従い、すぐに「変更」の判断として記録に書く。指示がどちらを意図するか読み切れないときだけ、食い違い（記録の判断と、いまの指示）を示して確かめる。
- 圧縮のあとは、SessionStart のフックが、一つ前の圧縮の境目（無ければ会話の始め）より後の端末からの入力を原文で差し込む。これをいまの会話の指示として、記録より先に読む。記録に無い判断がそこにあれば、記録に書く。圧縮の要約と記録が食い違えば、差し込まれた原文か会話の記録で確かめる。

## 判断を変えるとき

- 古い判断の見出しと本文を書き換えない。「変更」の判断を新しく足し、古い判断の「状態」を「置き換え済み（<新しい判断の見出し>）」に直す。
- 棄却した案を出し直すのは、棄却のときに無かった事実が出たときだけ。新しい事実を「判明した事実」に書き、「リーダーに決めてほしいこと」で問い直す。

## 直すとき

- 「いまの方針」「いまの作業」「済んだこと」「残っていること」「次に Claude がすること」「リーダーに決めてほしいこと」は、今の姿に書き直す（追記を重ねない）。
- 直したら、作業と同じブランチにコミットする。メッセージは `docs(work): <何が変わったか>`。
- memory、issue のコメントと記録が食い違ったら、記録の新しい判断に従い、食い違う側を直すか、直せない物（他人の文、過去のコメント）は記録の「判明した事実」に食い違いを書く。
- 記録の判断を根拠に CLAUDE.md の行を直さない。食い違いを理由に CLAUDE.md の行を直すのは、いまの会話でリーダーの指示がその決まり自体を変えるもの（「今後」「決まりとして」など）のときだけ。
- 記録の判断が CLAUDE.md の決まりと食い違えば、リーダーが決めたと確かめられない間は CLAUDE.md に従い、食い違いを「リーダーに決めてほしいこと」に書く。Claude の判断なら、記録の判断を「変更」で改める。安全と権限の決まりの行と、CLAUDE.md の「作業記録」の節で緩めない、消さないと書いた行は、リーダーの指示なしに緩めない、消さない。

## 着手のとき

1. `docs/work/` に同じ作業の記録があるかを見る（SessionStart のフックが、開いている記録の一覧を出している）。
2. あれば全部読み、「次に Claude がすること」から続ける。この会話の依頼が別にあれば、依頼を先にする。記録が会話や現物と食い違っていれば、先に記録を直す。
3. 無ければ作る。目的の原文は `prts quote` で確かめて引く。過去の issue のコメントや memory から判断を移すときは、原文を確かめられた物だけを「採用」「棄却」として書き、確かめられない物は「判明した事実」に「未確認の過去の記録」として書く。
