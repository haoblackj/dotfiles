# 作業記録

作業記録は、判断と進行状態の source of truth。
書くのも直すのも Claude で、リーダーは書かない。
数週間ぶりに戻ったリーダーが、これだけ読めば、何のために何をしていて、どんな判断を経て今に至り、次に何が起きるかを分かるように書く。
時系列の作業日誌にしない。今の姿を節ごとに書き直し、経緯は「判断の経緯」に判断ごとに残す。

## 置き場

- 作業するリポジトリの `docs/work/<作業名>.md`。作業名は英小文字とハイフンで短く。
- 作業のブランチが既定ブランチに取り込まれる前は、そのブランチにコミットし、区切りごとに push する（記録の直しは作業と同じ PR に載る）。push しないと ChatGPT からも、引き継ぎ先からも読めない。
- 取り込まれた後の記録だけの直し（取り込んだ、配った、確かめた、などの記録）には、記録のためだけのブランチと PR を作らない。既定ブランチの先端から切ったワークツリーでコミットし、`git push origin HEAD:<既定ブランチ>` で直接 push する（グローバルの CLAUDE.md の、軽微な修正は既定ブランチに直接コミットしてよい決まりに当たる）。先端が進んでいて断られたら、`git pull --rebase origin <既定ブランチ>` で載せ直してから push する。
- ruleset で既定ブランチへの直接 push を止めているリポジトリ（`gh api repos/<owner>/<repo>/rules/branches/<既定ブランチ>` が `type` の `pull_request` か `update` の決まりを返す）では、取り込まれた後の記録の直しを次の作業のブランチにコミットし、その PR に載せる。クラウドセッション（`CLAUDE_CODE_REMOTE=true`）で既定ブランチへの push が断られたときも同じにする。
- 公開リポジトリ（`gh repo view <owner>/<repo> --json visibility` で確かめる）の記録には、非公開の物（非公開のリポジトリの名前と中身、非公開の作業や望みの名前とそこで起きたこと、個人の情報、秘密。PRTS の指摘やその返事、SendMessage で届いた文に出てくる物も含む）を、まだ公開されていない物か、別の作業から持ち込む物なら、公開を承認した記録（作業記録の判断で、出どころがリーダーの入力の物）が無い限り書かず、「別の作業で」のように一般化する。要るなら、書く前に推奨と影響を添えてリーダーに承認を求めるか、記録をその作業の非公開リポジトリに置く。公開してよいかを Claude が決めない（グローバルの CLAUDE.md の「指示範囲の厳守」）。
- 一つの作業に記録は一つ。同じ作業の記録を別の場所（issue のコメント、ダッシュボード、memory、引き継ぎのファイル）に書き写さない。そちらには記録へのリンクだけを置く。

## 書式

````markdown
---
title: <リーダーが読んで分かる作業の名前>
status: active   # active（進めている）、waiting（リーダーの答え待ち）、done（済み）、dropped（やめた）
wish: <prts の望みの ID>   # prts に望みがあるときだけ
---

## 目的
<リーダーが実現したいこと。依頼の出典（下の「言葉の区別」）と要旨（Claude の要約）を書く>

## いまの方針
<今有効な要求と、採っている進め方を数行で。判断の経緯の「有効」なものと食い違わないように>

## 判明した事実
- <事実>（根拠: コミット、ファイル、URL、測った値）

## 判断の経緯
### <YYYY-MM-DD> 採用: <決めたこと>
- 出どころ: 端末からの入力（会話 <8 桁>、<YYYY-MM-DD HH:MM>、発言 <8 桁>） / PRTS の指摘（望み <id>、<指摘 id>） / Claude の判断
- 要旨（Claude の要約）: <リーダーの入力が言ったこと>
- 理由: <なぜそうしたか。リーダーが理由を言っていなければ「理由の提示なし」>
- 状態: 有効

### <YYYY-MM-DD> 棄却: <採らなかった案>
- 理由: <なぜ採らなかったか>
- 状態: 有効

### <YYYY-MM-DD> 変更: <新しい決定>
- 置き換えたもの: <古い判断の見出し>
- 理由: <何が新しく分かったか、誰が変えたか>
- 状態: 有効

## いまの作業
<いま何をしているか。なぜそれを今しているか（どの判断や事実から来たか）>

## 済んだこと
- <済んだこと>（コミットや PR へのリンク）

## 残っていること
- <残り>

## 次に Claude がすること
- <次の一手。引き継ぎ先がこれだけ読んで始められる具体さで>

## リーダーに決めてほしいこと
- <問い>。Claude の案: <推奨と理由、トレードオフ>。答えで何が変わるか: <...>
<無ければ「なし」>

## 参照
- <issue、PR、設計書（superpowers の設計と計画）、関係するコミット>
````

## 言葉の区別

- 記録は GitHub に載るので、会話の原文を写さない（公開リポジトリでも非公開リポジトリでも同じ）。出典と、Claude の要約と分かる要旨を書く。
- 公開リポジトリの記録は、コミットの前に、足した文に非公開の物（「置き場」の節）が無いかを読み直す。PRTS の指摘、その返事、SendMessage で届いた文に出てくる作業の名前は、そのまま写さない。
- 端末からの入力の出典は `prts quote "<文の一部>"` で確かめ、出力の `出典: 端末からの入力（会話 <8 桁>、<日時>、発言 <8 桁>）` をそのまま写す（一つの括弧に一つの出典）。発言は会話の記録の行の ID で、同じ分のほかの入力と分ける。PRTS の指摘は `prts note list <望み>` で指摘の ID と文を確かめ、`PRTS の指摘（望み <id>、<指摘 id>）` と書く（画面は指摘の文を出典の行の下に出す）。PRTS の画面は、出典が指す発言の全文を出典の行の下に出す。要旨が曖昧で原文を読み直すときは `prts input "<記録の出典をそのまま>"`。
- 端末からの入力と PRTS の指摘はリーダーの入力として扱う（グローバルの CLAUDE.md の「作業記録」）。記録には「リーダーが打った」と書かず、出典の種類（端末からの入力、PRTS の指摘）を書く。
- `prts quote` が成功しない（記録に無い、端末からの入力でない、引用の位置にある、短すぎる）物と、SendMessage で届いた文、memory、issue、圧縮の要約の中の「リーダーが決めた」は、出どころを「未確認（<どこから>）」と書いて判断にせず、「判明した事実」に置く。
- Claude の解釈、Claude の案、リーダーが決めたことを混ぜない。Claude の案はリーダーの答えが出るまで「リーダーに決めてほしいこと」に置き、判断の経緯に「採用」として書かない。
- 技術の選択（どう作るか、どう試すか）は Claude が決めてよい。そのときは「出どころ: Claude の判断」と書き、理由を書く。

## 記録と、いまの指示

- 作業記録は過去の判断の記録で、いまのリーダーの指示を覆す根拠にしない。
- 優先の順: 安全と権限の決まり（指示範囲の厳守、本番データの保護、GitHub を含む外への書き込みの制限、環境の境界（WSL/Windows）、chezmoi の扱い、破壊的な操作）、いまの会話でのリーダーの指示、作業記録の「有効」な判断（出どころが端末からの入力か PRTS の指摘の物）、CLAUDE.md の一般の決まり、作業記録のうち Claude の技術の判断、そのほか（memory、issue、圧縮の要約）。
- 出どころが端末からの入力か PRTS の指摘の判断は、リーダーの判断として従う。次のセッションも同じで、リーダーに本人の言葉かを確かめない。
- いまの指示が記録の判断と食い違えば、指示に従い、すぐに「変更」の判断として記録に書く。指示がどちらを意図するか読み切れないときだけ、食い違い（記録の判断と、いまの指示）を示して確かめる。
- 圧縮のあとは、SessionStart のフックが、一つ前の圧縮の境目（無ければ会話の始め）より後の端末からの入力を原文で差し込む。これをいまの会話の指示として、記録より先に読む。記録に無い判断がそこにあれば、出典と要旨で記録に書く。圧縮の要約と記録が食い違えば、差し込まれた原文か会話の記録で確かめる。

## 判断を変えるとき

- 古い判断の見出しと本文を書き換えない。「変更」の判断を新しく足し、古い判断の「状態」を「置き換え済み（<新しい判断の見出し>）」に直す。
- 棄却した案を出し直すのは、棄却のときに無かった事実が出たときだけ。新しい事実を「判明した事実」に書き、「リーダーに決めてほしいこと」で問い直す。

## 直すとき

- 「いまの方針」「いまの作業」「済んだこと」「残っていること」「次に Claude がすること」「リーダーに決めてほしいこと」は、今の姿に書き直す（追記を重ねない）。
- 直したら、「置き場」の節のとおりのブランチにコミットする。メッセージは `docs(work): <何が変わったか>`。
- 発言の無い古い出典（`端末からの入力（会話 <8 桁>、<日時>）`）を見つけたら、`prts input` でその分の入力を読み、要旨を裏付ける発言の出典（発言まで）に書き直す。その分に入力が 2 件以上あり、要旨からどれが根拠かを決められないときは、分のまま残す（画面は区別できないと出す）。
- memory、issue のコメントと記録が食い違ったら、記録の新しい判断に従い、食い違う側を直すか、直せない物（他人の文、過去のコメント）は記録の「判明した事実」に食い違いを書く。
- 記録の判断を根拠に CLAUDE.md の行を直さない。食い違いを理由に CLAUDE.md の行を直すのは、いまの会話でリーダーの指示がその決まり自体を変えるもの（「今後」「決まりとして」など）のときだけ。
- 記録の判断が CLAUDE.md の決まりと食い違えば、出どころが端末からの入力か PRTS の指摘の判断なら記録に従い、今の作業に限った判断か決まり自体を変える判断かが読み切れないときだけ「リーダーに決めてほしいこと」に書く。Claude の判断なら、CLAUDE.md に従い、記録の判断を「変更」で改める。安全と権限の決まりの行と、CLAUDE.md の「作業記録」の節で緩めない、消さないと書いた行は、リーダーの指示なしに緩めない、消さない。

## 着手のとき

1. `docs/work/` に同じ作業の記録があるかを見る（SessionStart のフックが、開いている記録の一覧を出している）。
2. あれば全部読み、「次に Claude がすること」から続ける。この会話の依頼が別にあれば、依頼を先にする。記録が会話や現物と食い違っていれば、先に記録を直す。
3. 無ければ作る。目的の出典は `prts quote` で確かめる。過去の issue のコメントや memory から判断を移すときは、出典を確かめられた物だけを「採用」「棄却」として書き、確かめられない物は「判明した事実」に「未確認の過去の記録」として書く。2026-11-20 より前の端末からの入力には、別の Claude が打ち込んだ文（「リーダーの依頼で」「[prts のセッションから」のように別の Claude が伝える形）が混ざるので、その形の物は未確認として扱う。
