## 目的

pre-push のテストが遅すぎるので、実態と原因を調べる（出典: 端末からの入力（会話 e649f52f、2026-11-22 22:29、発言 28cc0de4）。要旨は Claude の要約）。
調べた結果を受けて、bats を並列で走らせ、本物の Haiku を呼ぶテストを偽物に替える（出典: 端末からの入力（会話 e649f52f、2026-11-22 22:42、発言 22560e63）。要旨は Claude の要約）。
それでも長いので、テストの数そのものを必要最小限に減らす（出典: 端末からの入力（会話 e649f52f、2026-11-22 22:51、発言 9910e608）。要旨は Claude の要約）。

## いまの方針

pre-commit の bats フックは、GNU parallel があればコアの数だけ並列に走らせ、無ければ順に走らせる。
`session-title-promote.bats` は `PATH` の先頭に偽の `claude` を置き、渡した引数と、答えを採るか捨てるかを確かめる。
bats のテストは、判断の経緯の基準で選んだ 99 件と、Herdr のタブ名の同期のテスト 37 件（専用のファイル 33 件と statusline 側の 4 件）を残す。合わせて 136 件。

## 判明した事実

- 直す前の pre-push の段（`pre-commit run --hook-stage pre-push --all-files`）は CLOCK_MONOTONIC で 101.6 秒。bats が 97.2 秒、pytest が 2.8 秒、sp-repo-review が 0.3 秒（2026-11-22 に測った値）。
- bats は 365 件を 1 コアで順に走らせていて、CPU の使用率は 53%。マシンは 16 コア。
- `session-title-promote.bats` の 7 件が本物の `claude -p --model haiku` を呼び、合わせて約 22 秒かかっていた。push のたびに利用枠も使っていた。
- 時間切れを待つ作りのテストが合わせて約 17 秒（herdr が固まる場合、codexbar の serve が応答しない場合、statusline の herdr が遅い場合、usage-route のサーバーに届かない場合と応答しない場合）。テストを減らしたときに、待つテストはすべて消した。
- WSL の CLOCK_REALTIME が約 5.5 秒ごとに前後へ飛んでいて、`bats -T` のテストごとの時間が見かけで 7.5 秒前後になる。本題と別のバグとして `ideas/bugs/2026-11-22-wsl-realtime-clock-jumps.md` に書いた。
- 直した後の pre-push の段は、3 回続けて 19.0 秒、22.2 秒、21.1 秒で、3 回とも全部通った。GNU parallel が無い場合（moreutils 風の `parallel` を `PATH` の先頭に置いた）は順に走って 76.4 秒で、全部通った。
- テストを 366 件から 90 件に減らした後の pre-push の段は、3 回続けて 8.0 秒、7.0 秒、6.8 秒で、3 回とも全部通った。bats だけなら並列で 4.4 秒。GNU parallel が無い場合は 17.5 秒で、全部通った。
- 分類はサブエージェントが全 366 件に付け（残す 87 件、消す 279 件）、Claude が消す側を読み直して、壊れると黙って害が出る 3 件（退避先のリポジトリを新しく作らない、復元に失敗したら済んだ印を付けない、data の型の間違いで黙って描かない）を残す側へ戻した。
- コードレビュー（requesting-code-review）で、基準に当たるのに消していた 9 件が見つかり、戻した（skills 配下の *.json を自動コミットに入れない回帰、退避の失敗を隠さない 5 件、前置き付きの gh を読む 2 件、chezmoi のある環境で install-cloud が何もしない 1 件）。戻した後は 99 件で、並列 4 回とも全部通り、pre-push の段は 7.5 秒と 7.9 秒、GNU parallel が無い場合は 18.6 秒。
- 基準を選ぶときの案の文で、Herdr のタブ名の同期を「呼ばれていない」と書いたのは正確でなかった。statusline が更新のたびに背景で呼んでいて、Herdr の中で動くとき（`HERDR_ENV=1`）だけ働く。いま Herdr のプロセスは動いていない。消したテストには、手で付けたタブ名を上書きしない（#91）と、herdr が固まったときに打ち切る、の再発防止が入っていた。
- Herdr のタブ名の同期のテストを戻した直後は 136 件で、並列 4 回とも全部通り、pre-push の段は 14.5 秒と 13.4 秒、GNU parallel が無い場合は 31.1 秒。並列の時間は、Herdr が固まる場合を待つ 1 件（スクリプトの本体が `timeout 5` で待つ）がおよそ 5 秒の下限を作っていた。
- Herdr が固まる場合と、statusline が Herdr を待たない場合の 2 件を、本物の待ち時間を待たずに確かめる形に替えた（コミット f83c88b）。本体の `timeout 5` と背景の `&` を一時的に抜くと落ちることを確かめた。替えた後は 136 件で、並列 4 回とも全部通り、bats は 5.0〜6.3 秒、pre-push の段は 9.1 秒と 8.6 秒、GNU parallel が無い場合は 26.4 秒。
- 本番の作業コピー（`~/.local/share/chezmoi`）では、pre-push の `bats -r .` が `.claude/worktrees/` の下の 7 つのワークツリーのテストまで拾い、156 ファイル、3362 件を走らせていた（追跡しているのは 18 ファイル、365 件。2026-11-22 に数えた値）。別のセッションが本番の作業コピーに書き置いた `ideas/bugs/2026-11-22-pre-push-bats-runs-worktrees.md`（未追跡）に、push が 10 分の上限を超えたことが書かれている。上の測った値はどれも、中に別のワークツリーが無い Orca のワークツリーで測ったもので、この分が入っていない。
- 本番と同じ形（このワークツリーの `.claude/worktrees/` の下に、本番と同じ 7 つのコミットの別のワークツリーを置いた。見える `.bats` は 156 ファイル）で、直す前の bats の段は 3133 件を走らせて 159.6 秒だった。直した後は 137 件だけを走らせ、bats の段は 9.8 秒と 10.2 秒、pre-push の段全体は 15.9 秒と 15.6 秒、GNU parallel が無い場合は 29.7 秒。どれも全部通った。
- 直した後は、別のワークツリーがあってもなくても bats の段は 10〜11 秒で変わらなかった。測ったときの load average は 12.8 で、ほかのセッションが CPU を使っていた分、前に測った 5.5 秒より遅く出た。
