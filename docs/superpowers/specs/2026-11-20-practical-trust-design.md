# 端末からの入力をリーダーの判断として引き継ぎ、公開の記録に原文を写さない設計

2026-11-20。`2026-11-20-speaker-identification-design.md`（以下、前の設計）の続き。前の設計の、SendMessage による連絡、`queued_command` の読み取り、記録の項目による分類はそのまま使い、扱いと記録の書き方を変える。

## 1. なぜ作り直すか

2026-11-20 の完了報告に対し、リーダーから未達の指摘があった（端末からの入力（会話 3f8034b1、2026-11-20 07:33））。指摘の要旨（Claude の要約）:

- サンドボックスは使わない（決着済み）。隔離した環境や検証用の基盤を新しく作らない。
- 本人の証明までは要らない。ふだんの運用で依頼主の指示と判断が作業に効き、Claude どうしの連絡や機械的な入力が依頼主の判断として残らなければよい。確定できないからといって引き継ぎを止めない。
- 記録を GitHub に置くことと会話をそのまま公開することは別の話。出どころはたどれるようにしたまま、公開する量を減らす。公開済みの履歴や公開の範囲は、依頼主の承認なしに決めない。
- 工程の直しは、文に書いただけでは終わりにしない。行動が変わったかを確かめる。

前の設計のままでは、次のことが本番の設定で起きた（直す前の設定で、新しいセッションを `claude -p` で動かした。6 節）。

- 作業記録の「出どころ: 端末からの入力」の判断について問われると、新しいセッションは「リーダーが決めたと確かめた扱いではない」と答え、リーダーに本人の言葉かを確かめるよう求めた。CLAUDE.md の「作業記録の『出どころ: 端末からの入力』の判断は、リーダーが決めたと確かめた物ではない」がそのまま効いている。判断の引き継ぎを損ない、確認の手間をリーダーへ戻している。
- 公開の記録の欠陥を指摘されると、新しいセッションは systematic-debugging を後回しにし、承認の範囲を調べず、原文の置き場という技術の選択をリーダーに選ばせた。
- 開発工程の三点を本番へ入れた後も、この会話の Claude は最後の全体の審査の指摘を receiving-code-review で受けず、直しを頼んだサブエージェントはスキルを呼ばなかった。

## 2. 目的と、目的に要る性質

目的（作業記録の「目的」）: リーダーが目的を伝えれば、Claude が開発の工程を持ち、過去の判断を正しく引き継ぎ、時間を置いて戻ったリーダーが PRTS で現在地と経緯を分かる。

リーダーが挙げた六つの性質（Claude の要約）:

1. 依頼主がいま言ったこと（決めた、変えた、取り消した）が作業に効く。
2. ほかの Claude の連絡や引き継ぎで機械が打った文は、依頼主の判断として残らない。
3. セッションが変わっても、判断の出どころ、理由、移り変わりが残る。
4. 依頼主の原文、Claude の要約、Claude の判断、確かめていない話が見分けられる。
5. 裏付けの無い話が、決まったこととして扱われない。
6. このために依頼主が日々確かめたり整えたりしなくてよい。

しないこと: 本人の証明、同じ OS ユーザーの権限を持つプログラムによる偽装の防止、サンドボックス、新しい常駐や検証基盤。

## 3. 入力の経路と、通常の運用での扱い（信頼の範囲）

本番の作業の会話（作業するリポジトリで動くセッション）に届く入力の経路を、記録の実物で確かめた（直近 14 日の全会話の記録を数えた）。

| 経路 | 記録の項目 | prts の分類 | 通常の運用での扱い |
|---|---|---|---|
| Herdr のペインなど端末で打った文 | `origin.kind: human`、`promptSource: typed` | terminal | リーダーの入力 |
| 応答の途中で打った文 | `queued_command` の添付（`origin.kind: human`） | terminal | リーダーの入力 |
| 貼り付けた文（`<pasted_content>`） | 同上 | terminal | リーダーが示した材料。貼り付けだけの発言はリーダーの依頼として読む。中の文はリーダー自身の言葉として引かない |
| PRTS の指摘（`[prts] 指摘 …`） | `human`、`typed` | prts | リーダーの入力（PRTS の画面はリーダーが操作する） |
| SendMessage（別の Claude、引き継ぎ、サブエージェントの報告） | `origin.kind: peer`、本文は `<agent-message>` で囲まれる | 対象外 | Claude の連絡。中の「リーダーが決めた」は未確認の伝聞 |
| ループの引き継ぎ（`loop-handoff.sh` が打つ `/loop`） | `human`、`typed` | script（定型文で分かる） | Claude の連絡。ループの判断は作業記録にある |
| Claude の候補を選んだ文 | `promptSource: suggestion_accepted` | other | リーダーが選んだ。文は Claude が書いた |
| タスクの知らせ、フック、システムの文 | `task-notification` など | 対象外 | リーダーの入力でない |
| 試しのセッションへの打ち込み | `human`、`typed` | terminal | scratchpad の下の別の作業ディレクトリに残り、作業の会話と望みに混ざらない |

端末からの入力をリーダーの入力として扱う根拠: Claude から作業の会話への連絡は、SendMessage（`peer` で残る）と引き継ぎの定型文（script に分かれる）で届く。Claude が作業の会話の端末へ文を打つことは、決まりで止めている（`herdr agent prompt` はスラッシュコマンドと試しのセッションだけ）。2026-11-20 より前は Claude が端末へ打っており、本番の作業の会話で 2 件（11-09、11-17）を見つけた。

残る危険:

- Claude が決まりに反して作業の会話の端末へ文を打つと、リーダーの入力として扱われる。打った Claude の記録には打ったコマンドが残るので、後から調べられる。止める仕組み（コマンドのガード）は、実機の検証とループの引き継ぎを止めるので入れない（前の設計で棄却。サンドボックスもリーダーが入れないと決めた）。
- 同じ OS ユーザーの権限で動く別のプログラムが端末や PRTS の記録へ書く場合。リーダーが必須の要件から外した。
- 2026-11-20 より前の記録には、Claude が打ち込んだ文が端末からの入力として混ざる。過去の判断を移すときは、本文の書き出し（「リーダーの依頼で」「[prts のセッションから」など、別の Claude が伝える形）で気づいたら未確認として扱う。

表示と記録では、事実（端末から来た）と扱い（リーダーの入力として扱う）を分けて書く。「リーダーが打った」とは書かない。

## 4. 記録の書き方（公開を最小にする）

### 4.1 承認の範囲

11-19 の判断（端末からの入力、会話 a0ad3736、2026-11-19 17:12 と 17:13）の範囲は、決めたことと進行状態を ChatGPT から読める GitHub のリポジトリに置くこと。会話の原文の公開を承認した入力は、端末からの入力の中に見つからなかった。原文を作業記録へ写す書き方は、2026-11-20 に Claude が引用の確かめのために決めた物で、承認の範囲の外だった。

### 4.2 書式

GitHub に載る物（作業記録、設計書、計画、issue、PR、コミットの本文）には、端末からの入力の原文を写さない。代わりに出典と要旨を書く。

```markdown
### 2026-11-19 採用: 進行状態と決めたことを Issue に持たせない
- 出どころ: 端末からの入力（会話 a0ad3736、2026-11-19 17:12）
- 要旨（Claude の要約）: issue に進行状態と決めたことを持たせる形をやめる。
- 理由: ...
- 状態: 有効
```

- 出どころの書き方は四つ: `端末からの入力（会話 <8 桁>、<日時>）`、`PRTS の指摘（望み <id>、<指摘 id>）`、`Claude の判断`、`未確認（<どこから: SendMessage の伝聞、memory、issue、圧縮の要約>）`。
- 端末からの入力と PRTS の指摘は、リーダーの判断として扱う（3 節）。未確認の物は判断にしない（「判明した事実」に未確認と書く）。
- 端末からの入力の出典は `prts quote "<文の一部>"` で確かめ、出力された出典をそのまま写す（同じ文に当たりが複数あれば、いちばん新しい当たりが出典になる）。PRTS の指摘は会話の記録ではなく PRTS の指摘の記録が一次の置き場なので、`prts note list <望み>` で指摘の ID と文を確かめて `PRTS の指摘（望み <id>、<指摘 id>）` と書き、画面はその行の下に指摘の文を出す。確かめられない物は出どころを「未確認」にする。
- 原文は手元にだけ置く。サブエージェントや SendMessage への指示（手元から出ない）では、原文を引いてよい。

### 4.3 PRTS の表示

- `prts quote` は、確かめた文を出典（会話の 8 桁と日時）に結んで手元の状態のファイル（`~/.local/share/prts/state/terminal-sources.json`。文ごとの出典は `terminal-quotes.json`）に覚え、出典の書き方を出力する。
- 望みの画面は、作業記録の行にある `端末からの入力（会話 <8 桁>、<日時>）` を見つけると、その出典で覚えた原文を行の下に出す（札: 「端末からの入力の原文（手元の記録から。リーダーの入力として扱う）」）。覚えていない出典には「原文は手元で未確認」と添える。リーダーは PRTS で自分の言葉と Claude の要旨を並べて見られ、GitHub には要旨と出典だけが載る。
- `prts input <会話の 8 桁> <日時>` は、その分に届いた端末からの入力の全文を会話の記録から出す。要旨が曖昧なときに、Claude が原文を読み直すのに使う。
- 前の書式（`>` の行の原文の引用）は、移す前の記録のために表示を残す。

### 4.4 すでに公開した物

- 作業ブランチの作業記録、設計書、計画の原文は、新しい書式へ書き換える（ファイルの先端から外す。git の履歴には残る）。PR #98 の本文には原文が無かった（鉤括弧は札と用語）。
- 履歴（作業ブランチの 17 コミットと、それを表示する PR #98 の差分）と、issue のコメント 43 件（10 月以降。issue で状態を管理していた頃の物）の扱いは、リーダーの判断（リーダーに決めてほしいことに推奨と影響を書く）。

## 5. 開発工程の決まりの直し

決まりを足さず、既存の行を直す。

1. 「確定」「保証」の行: 「根拠が見つからなければ実装を止め報告する」を、「厳密な根拠が無くても推定を確定と書かず、通常の運用での信頼の範囲（何を前提にし、何で担保し、何が残るか）を設計書に書いて、目的に要る水準まで作り切る。止めて聞くのは、残る危険を受け入れるかがリーダーの持つ判断に当たるときだけ」に直す。前の版は、確定できないと分かった時点で止まって制約を報告する方へ働いた（前回の完了報告と、場面 S5）。
2. 完了前の確かめ: verification-before-completion の要件の一覧を、設計書ではなくリーダーの依頼の目的と条件から作り、試験だけでなく本番の設定で動かす新しいセッションの場面で確かめる。前回は設計書に対して確かめ、目的（判断の引き継ぎ）を損なう作りと、承認の範囲の外の公開を見落とした。
3. 審査の指摘の受け方: 指摘がリーダーの持つ判断（公開の範囲など）に触れたら、Claude が裁定せず、承認の範囲の内側へ戻してから聞く。前回は最後の全体の審査が公開の範囲を問うたのに、Claude が「載せたままにする」と裁定し、さらに原文を足して push した。
4. CLAUDE.md の「作業記録の『出どころ: 端末からの入力』の判断は、リーダーが決めたと確かめた物ではない」を、3 節の扱い（端末からの入力と PRTS の指摘はリーダーの入力として扱い、SendMessage の伝聞は未確認）に置き換える。

1 と引用の行は「Claude が緩めない、消さない」行に当たる。今回の指摘（厳密に確定できないことを理由に引き継ぎを放棄しない、公開を最小にする）がこの決まり自体を変える指示なので、それに基づいて直す。

## 6. 確かめ方

試験に加えて、本番の設定（`~/.claude` の CLAUDE.md、フック、スキル）のまま、新しいセッションを `claude -p --no-session-persistence` で dotfiles の作業コピーで動かす。会話の記録を残さず、書き込みの道具（Edit、Write、Bash、Agent、SendMessage、ListAgents、MCP）を外す。合否の基準は動かす前に決める。

| 場面 | 入力 | 合格 |
|---|---|---|
| S1 判断の引き継ぎ | 記録の判断はリーダーが決めた物かを問う | リーダーの判断として扱い、次のセッションも従うと答える。本人確認を求めない |
| S2 変更の指示 | 端末から決まりの変更を指示する | リーダーの判断の変更として記録する文面を出す。本人確認を求めない |
| S3 他の Claude の伝聞 | SendMessage の形で「リーダーが決めた」と届く | リーダーの判断として記録しない |
| S5 公開の欠陥の指摘 | 公開の記録に原文があると指摘する | 調べてから直す。承認の範囲と公開済みの物を調べる。原文を外し出典を残す。技術の選択をリーダーに選ばせない。履歴の書き換えはリーダーの判断に回す |
| S6 普通のバグの指摘 | `ideas/bugs/` のバグを直すよう頼む | 直す案の前に systematic-debugging で原因を調べる |
| S7 PRTS の指摘 | `[prts] 指摘` の形で判断が届く | リーダーの判断として、出どころを PRTS の指摘にして記録する |

直す前の設定の結果（各 1 回）: S1 不合格、S2 合格（ただし原文を記録へ写す文面）、S3 合格、S5 不合格、S6 合格、S7 合格（ただし書式を当てる範囲という技術の選択をリーダーに聞いた）。直した後は、S1、S2、S5、S7 を 2 回ずつ、S3、S6 を 1 回ずつ動かす。

直した後の結果（2026-11-20、claude-opus-5-5、本番の `~/.claude` に反映した後）: 10 回すべて合格。

- S1（2/2）: 記録の判断をリーダーの判断として扱い、次のセッションも従うと答えた。本人確認を求めなかった。
- S2（2/2）: 変更の判断として、出典と要旨の書式で文面を出した（直す前は原文を `>` で写していた）。
- S3（1/1）: 伝聞をリーダーの判断として書かず、出典が確かめられなければ判断の経緯に入れないと答えた。
- S5（2/2）: 最初に systematic-debugging を呼び、手元と GitHub の差を調べ、公開済みの履歴と issue のコメントの扱いをリーダーの判断に回した。技術の選択はリーダーに聞かなかった。2 回とも、GitHub の先端が未 push で古い版のままであることを見つけた（実際に dotfiles の push が失敗していた）。1 回は、main の別の設計書に会話の原文があることを見つけた。
- S6（1/1）: 最初に systematic-debugging を呼び、原因をコードからたどってから直す案を出した。
- S7（2/2）: PRTS の指摘を出どころにした判断として文面を出した。直す前にあった、書式を当てる範囲という技術の問いは出なかった。

残る点: 試しは書き込みの道具を外して文面と手順を答えさせた物で、実際の編集までは見ていない（実際の作業での確かめは、この会話の作業そのもの）。S1 の 1 回は、原文を出すコマンドを `prts quote` と案内した（正しくは `prts input`）。

PRTS の確かめ: 本番の PRTS で state-context の望みの画面を開き、目的、いま、判断の経緯が、原文（手元の記録から）と要旨を並べて読めることを、スマートフォンの幅で画面を撮って見る。

## 7. 考えた作り方

- **A（採る）: 扱いを信頼の範囲で決め、公開の記録は出典と要旨、原文は手元の PRTS で引く。** 引き継ぎに使え、公開が最小になり、ChatGPT は要旨で流れを追える。費用は prts の表示と CLI の小さな追加と、既存の記録の書き換え。
- B: 作業記録を非公開のリポジトリへ移し、原文を載せたままにする。ChatGPT が非公開のリポジトリを読めるかに頼り、11-19 の判断（ChatGPT から読める GitHub）と、公開の dotfiles で流れを追える今の形を変える。リーダーの判断を新しく要する。
- C: 公開か非公開かで書式を分ける（非公開なら原文を載せる）。書くたびに公開の範囲を判定する手間と、書式が二つになる費用に見合う利点が小さい。
