# 発言元の識別と、開発工程の立て直し（設計）

対象: dotfiles（ブランチ `ops/work-records`）と prts（ブランチ `feat/work-record`）。関連: haoblackj/dotfiles#86、作業記録 `docs/work/claude-ops-records.md`。

## 1. 目的と、なぜ

リーダーは開発者ではなく、目的を伝えれば Claude が開発の品質を自分で保ち、判断の記録を正しく引き継ぐことを求めている。
2026-11-20 に二つの問題が見つかった。

1. 発言元を証明できない入力を、リーダー本人の発言として扱っていた。`prts quote` は、時刻の近さや文字の一致から発言者を推し量り、推定を「リーダー」と表示していた。
2. superpowers を開発工程に採っているのに、修正の作業で関連のスキルを一つも呼ばず、レビューで設計の前提を否定されても、方式を見直さず修正を重ねた。

リーダーの指示（2026-11-20、会話 3f8034b1 への貼り付けの依頼）の要点:
- Claude Code 標準のセッション間通信を優先候補に、Herdr による起動、引き継ぎ、通常の対話との整合を調べ、新しいセッションへの最初の指示に使えるかを既存環境で確かめる。
- 今後の入力で、Claude の連絡とリーダー本人の入力を区別できる構成にする。保証できないことが残るなら、推定を確定として扱わず、保証できる範囲を示す。
- 過去の記録で確認できない発言を、リーダー本人の言葉と認定しない。queued_command の取りこぼしを直す。
- superpowers が使われなかった原因を CLAUDE.md、スキル、作業履歴から判断し、「必ずスキルを使う」という規則の追加で済ませない。今回の問題で、要求を満たせない方式を採らないか、前提を否定されたときに判断し直せるかを確かめる。
- dotfiles の未対応のレビュー指摘も解消する。main へのマージはしない。

## 2. 実証した事実（2026-11-20）

- Claude Code の会話の記録で、`origin.kind` は human、peer、plugin、task-notification、coordinator、unclassified がある。peer は送り手の項目（`from` のソケット、`verifiedPeerPid`、`verifiedPeerProcStart`、`msg_id`、`name`）を持ち、`isMeta: true`、`promptSource: system`。
- Herdr の `agent prompt`、tmux の `send-keys`（推定）、リーダーの手入力は、どれも `origin.kind: human`、`promptSource: typed`（作業中なら queued）で残り、記録の項目でも入力の履歴（`~/.claude/history.jsonl`）でも区別できない。Herdr のログは操作の種類と時刻だけで、送り先と文を残さない。
- Herdr で立てた新しいセッション（`herdr agent start <name> --kind claude --pane <pane> -- --name <題>`、最初の指示なし）は、約 5 秒で `ListAgents` に名前で出る。そこへ `SendMessage` で送った最初の指示を、相手は読んで作業した（試しのセッション `8b14d789-17fc-4c84-8f6b-6ce6a5910cfc` の 15 行目。`origin.kind: peer`、`verifiedPeerPid` は送ったこのセッションのプロセス、`msg_id` は送信の結果と一致）。
- `SendMessage` は、相手の権限のモードが違うと、相手の利用者の承認待ちになる（ツールの説明）。手元の設定の既定は auto で、Herdr で立てるセッションも同じ。
- 作業の途中で届いた入力は `type: attachment`、`attachment.type: queued_command`、`attachment.prompt` に本文、`attachment.origin: {kind: human}`、`humanTurn: true` で残る。`promptSource` は無い。今の `prts` の `user_utterances` は `type: user` しか読まず、これを落とす。
- `/loop` のようなスラッシュコマンドは、端末から打った入力でないと実行されない（peer の文として届いた `/loop` が実行されるかは確かめていない。安全のため、端末から打つ前提を残す）。

## 3. 目標、目標でないこと、失敗とみなすこと

目標:
- Claude からの連絡（引き継ぎの指示、セッションどうしの知らせ）が、記録の上で送り手つき（peer）で残る。
- `prts quote` と `prts candidates` が、記録から確定できる性質だけで入力を分類し、推定を確定として出さない。
- 端末から来た入力を「リーダーの入力（端末）」とするときの保証の範囲を、出力と文書に明記する。
- 切り替えより前の端末からの入力は、すべて「発言者を確定できない」にする。
- queued_command を人の入力として読む。
- superpowers の工程が、修正の依頼とレビューの指摘の場面で実際に使われる状態にし、今回の場面で確かめる。
- dotfiles のレビューの未対応の指摘を直す。

目標でないこと:
- Claude Code の外のプログラムが端末に書き込んだ文を見分けること（記録に手がかりが無い）。
- 送信の台帳や文字の照合による推定。
- Herdr や Claude Code 本体の改造。

失敗とみなすこと（動いても失敗）:
- 推定を「リーダー」と表示する経路が一つでも残る。
- 新しい決まりを足しただけで、今回の場面で判断が変わることを確かめていない。
- 引き継ぎやループの引き継ぎが動かなくなる。
- 安全のガード（破壊的な操作、GitHub の書き込み先、本番データ）や切り戻しの手段を弱める。

## 4. 案

- **A. 連絡の経路を分ける（採用、Claude の判断）。** Claude どうしの連絡と引き継ぎの指示は `SendMessage`（peer）に限り、Claude が Bash から端末へ文を打ち込む操作をガードで止める。端末から来る入力は、Claude の Bash からの送信ではないと言える。理由: 送り手の確認を Claude Code 本体が行い、推定を使わない。
- **B. 送信の台帳（不採用）。** herdr と tmux の呼び出しを中継して送った文を書き留め、届いた入力と文字で突き合わせる。文字の照合は推定で、一文字の違いや記録の漏れでリーダーの入力に化ける（2026-11-20 のリーダーの指摘）。
- **C. 発言元を名乗らない（不採用）。** 記録されないことを解決するための作業の目的に反する（2026-11-20 のリーダーの指摘）。
- **D. 時刻の近さ（不採用）。** 人がいつ打つかは決まっていない（2026-11-20 のリーダーの指摘）。

## 5. 設計（A）

### 5.1 dotfiles: 端末への打ち込みのガード

- PreToolUse（Bash）のフックを一つ足す。コマンドの中で、別の端末へ文を入れる呼び出しを止める。対象: `herdr agent prompt`、`herdr pane send-text`、`herdr pane send-input`、`herdr pane run`、文を含む `herdr agent send-keys` と `herdr pane send-keys`、`herdr agent start` の `--` より後ろの最初の指示（値を取らない位置の引数）、文を含む `tmux send-keys`（別名 `send` を含む）。キーの名前だけ（Enter、Escape、Tab、C-c、上下左右など）の send-keys は通す（フォルダの信頼の確認に Enter を送るため）。
- 止める理由の文: 別のセッションへの連絡は `SendMessage` で送る（受けた側の記録に送り手が残る）。新しいセッションへの最初の指示も `SendMessage` で送れる。
- 引き継ぎのスクリプト（`~/.claude/scripts/*.sh`）の中の呼び出しは、コマンドの文字に現れないので止まらない。スクリプトは下の 5.2 で、端末へ文を入れない形に変える（`/loop` を除く）。
- 保証の範囲: Claude の Bash のコマンドに直接現れる呼び出しは止まる。Claude が書いたプログラムやスクリプトの中から呼ぶ場合と、Claude Code の外のプログラムは止まらない。

### 5.2 dotfiles: 引き継ぎ

- `herdr-start-claude.sh` の `start_claude_in_new_tab` は、タブとセッションを立てるだけにし、最初の指示を打たない。最初の指示は、呼んだ Claude が `SendMessage` で `--title` の名前へ送る。
- `session-handoff.sh` は、引き継ぎの文（作業記録のパスと読み方）を JSON の `prompt` として返し、セッションを立てる。スキル `session-handoff` の手順で、Claude が `ListAgents` で名前を確かめてから `SendMessage` で送る。送れなかったら（名前が出ない、承認待ちの知らせ）、出力をリーダーに報告して止まる。
- `loop-handoff.sh` は `/loop` を端末から打つ必要があるので、今の形（スクリプトが `herdr agent prompt` で `/loop …（前のセッションからの引き継ぎ。…）` を打つ）を残す。prts はこの書き出しを「引き継ぎのスクリプト」として分類する。
- PRTS の「まとめて渡す」（`deliver.py`）は、PRTS のサーバーが Herdr で打つ。書き出し `[prts] 指摘` と、PRTS が保存した指摘の記録との突き合わせで分類する。

### 5.3 prts: 入力の分類

- `transcript.user_utterances` は、`type: user` の文字列（または文の塊の並び）に加え、`type: attachment` の `queued_command`（`attachment.prompt`、`attachment.origin.kind: human`）を読む。出どころ（`promptSource`、queued_command なら `queued_command`）を持たせる。peer など human でない物は、人の入力に含めない。
- `speaker` は記録から確定できる性質だけで分類する。時刻の照らし合わせ、送信の照合、Herdr のログの読み込みをやめる。分類:
  - `terminal`: 端末から打たれた入力（`promptSource` が typed か queued、または queued_command）で、切り替えの時刻以後のもの。表示は「リーダーの入力（端末から。Claude の Bash からの送信ではない）」。保証の範囲（5.1）を説明に添える。
  - `prts_note`: PRTS が送った束のうち、PRTS が保存した指摘（種類が「選択」でないもの）の文。表示は「PRTS の画面でリーダーが書いた指摘」。
  - `not_leader`: 引き継ぎのスクリプトとセッションどうしの知らせの決まった書き出しの文。
  - `unknown`: 切り替えより前の端末からの入力、Claude の候補を選んだ入力、プログラムからの入力、PRTS の案のボタンの文と定型の文、発言の中で鉤括弧やコードとして引かれた文、自分の文に添えて貼り付けた文。
- 切り替えの時刻は、5.1 のガードを本番に入れた時刻。prts の定数に置き、環境変数 `PRTS_INPUT_CUTOVER` で差し替えられるようにする。
- `prts quote` は `terminal` と `prts_note` だけを引用してよい物として成功させ、出力にその保証の範囲を書く。8 文字未満は断る。確かめた引用を覚える置き場は新しい名前にし、前の版の判定で覚えた物は使わない（前の置き場は trash-put で外す）。
- `wish add --pick` は `terminal` だけを原文にする。
- 画面の作業記録の `>` の行は、覚えた引用と一致すればリーダーの言葉の書体、しなければ「原文未確認」。
- 作業記録 `docs/work/claude-ops-records.md` の切り替えより前の引用は、`>` を外し、「会話への入力（発言者は確定できない）」と書き直す。

### 5.4 dotfiles: レビューの未対応の指摘

dotfiles のレビュー（2026-11-20）の指摘を直す:
- A1 圧縮のあとの差し込み: 「圧縮の要約と食い違えば記録に従う」を外す。基準を記録の mtime でなく、直前の圧縮の境目（無ければ会話の始め）にし、queued_command を含め、省いた件数と、全部を読むコマンド（`prts candidates --session <id>`）を示す。差し込む文には分類（5.3 と同じ考え方で、端末からの入力か）を添える。
- A2、C1、C2: 優先の順の「安全と権限の決まり」を定義する（指示範囲の厳守、本番データの保護、GitHub の名義と書き込みの制限、chezmoi の扱い、破壊的な操作）。作業記録の判断のうち、リーダーが決めた物だけを一般の決まりより上に置き、Claude の技術の判断は一般の決まりより下にする。安全と権限の決まりの行を緩める、消すのはリーダーの判断に戻す。スキル work-record の「食い違う側を直す」から安全の行を除く。
- A3: 異論の扱いの行を、Claude の技術の判断への異論に限ると書く。リーダーが「やめて」と言ったことは条件が無くても従う。
- A5: 着手のとき、この会話の依頼が別にあれば依頼を先にする。
- B: 引用の決まりを `prts quote` の分類に合わせる（CLAUDE.md の 15 行目と 185 行目付近、README、スキル session-handoff）。
- C3: 「指示範囲の厳守」のファイルの作成に、作業記録の作成と更新の例外を書く。
- D: 書き忘れの知らせは、記録の最後のコミットの時刻と HEAD を比べ、記録に未コミットの変更があれば知らせない。前書きの CRLF を読む。`check_state_file` は git の作業コピーかを `git rev-parse --show-toplevel` で確かめる。README の usage-route の表の古い行を直す。
- E: 上の各点の試験。

### 5.5 dotfiles: 開発工程

原因の判断は、実装の前に、CLAUDE.md、スキル、2026-11-20 の作業の記録から行い、設計書の付録に書く。直すのは原因に当たる所だけ。予定している方向:
- 修正の依頼（欠陥の指摘を受けた直し）は systematic-debugging から入る、と「開発の工程」に書く。
- レビューは requesting-code-review で頼み、戻った指摘は receiving-code-review で受ける。指摘が設計の前提（要件を満たせる根拠）を崩すときは、修正を足さずに systematic-debugging の「作りを問い直す」へ戻る。
- 要件が「確定」「保証」を求めるときは、その根拠になる情報源を実装の前に実測して設計書に書く。見つからなければ、実装せずに制約として報告する。
- 確かめ方: superpowers の writing-skills のやり方で、今回の場面（2026-11-20 01:33 の指示、案 1 の判定、レビューの 6 種類の抜け道）をサブエージェントに渡し、直す前と後の CLAUDE.md の文で、次に何をするかを比べる。直した後で「方式の問い直し」か「要件を満たせない制約の報告」を選ぶことを合格とする。

## 6. 本番への入れ方と切り戻し

- 順序: prts（分類と queued_command）を先に入れ、次に dotfiles（ガード、引き継ぎ、CLAUDE.md）。ガードを入れた時刻を切り替えの時刻にし、prts の定数を合わせて入れ直す。
- 切り戻し: dotfiles は `~/.local/share/chezmoi` で main へ切り替えて `chezmoi apply ~/.claude`。prts は main へ切り替えて `uv tool install --force --reinstall .`、`systemctl --user restart prts-web.service`。変更前の状態は `~/.cache/claude-ops-backup/20261120/`。
- 未コミットの変更は、作業を始める前に、今の作業ブランチへ「途中の状態」としてコミットして保全する。

## 7. 作り手に任せること

- prts の分類の名前と、出力の文面（保証の範囲を必ず含める）。
- 試験の書き方。

## 付録: superpowers の工程が使われなかった原因（2026-11-20 の記録から判断）

根拠: 会話 3f8034b1 の記録（`~/.claude/projects/-home-yagu001--local-share-chezmoi/3f8034b1-a008-4bec-a6ed-2bc115163166.jsonl`）、本番の `~/.claude/CLAUDE.md`、superpowers 7.0.2 のスキル。

1. 修正の作業（01:33 の指示から 02:14 まで）で呼んだのは、`general-purpose` のレビュー役 2 体（4254、4255 行目）と報告書のレンダラー（4892 行目）だけで、superpowers のスキルの呼び出しは 0 回だった。開始時と圧縮のあとに superpowers の導入文（using-superpowers）は差し込まれていた。導入文の「当てはまるなら必ず呼ぶ」という一般の指示は、あっても使われなかった。
2. CLAUDE.md の「開発の工程」は工程の名前を並べるだけで、どの場面でどのスキルから入るかを書いていない。修正の依頼の場面（指摘された欠陥を直す）は、superpowers では systematic-debugging の場面だが、CLAUDE.md にその対応が無い。さらに「設計の分かれ目が無い小さな変更は設計と計画を省いてよい」と書いてあり、修正の依頼を小さな変更として扱う余地があった。同じ行の「完了前の検証は省かない」も守られていないので、決まりの文を足すだけでは効かない。
3. CLAUDE.md の「仕事の任され方」の「設計書の承認を待たずに進め」「頼まれた成果物は全部済ませてから結果を報告する。途中経過で止まらない」は、止まらずに実装を続ける方向に働いた。「要件を満たせないと分かったら止まって報告する」場面が、どこにも書かれていない。
4. レビューの結果を受ける手順が無い。CLAUDE.md の審査の行は「一つの変更に一系統」だけを定め、指摘をどう受けるか（receiving-code-review）と、指摘が設計の前提を崩すときにどうするか（systematic-debugging の 195〜200 行目「直しが 3 回以上失敗したら止まり、作りを問い直す」）につながっていない。レビュー役への指示にも「設計の前提を崩す指摘か」を問う項目が無く、6 種類の抜け道は個別の直しの対象として返ってきた。
5. 要件の成立条件の確認が無い。指示は「発言者を確定できない」問題の解消で、確定の根拠になる情報源があるかを、実装の前に確かめる場面が無かった。01:33 に記録の項目で確定できないと確かめた直後に、推定の判定を書いた。

直すのは 2〜5 の場面への対応で、5.5 のとおり、今回の場面を使った試しで、直す前と後の判断の違いを確かめる。
