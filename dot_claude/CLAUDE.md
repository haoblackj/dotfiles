# グローバル個人ルール

全プロジェクト共通の個人ポリシー。プロジェクト側 CLAUDE.md はこれを継承する。

## クラウドセッション（環境変数 `CLAUDE_CODE_REMOTE=true`）での読み替え

クラウドでは、このファイルは dotfiles の `install-cloud.sh` が配ったもの。手元の WSL 前提の記述を次のとおり読み替える。

- 「ホーム配下の設定ファイルはchezmoi前提で扱う」「Herdr でのセッションの立て方」「環境の境界（WSL/Windows）」と、Codex への委譲の記述は適用しない。chezmoi / herdr / codex / trash-put はコンテナに無い。
- superpowers などのプラグインは入っていない。スキル名での指定は、同じ手順を自分で踏む指示として読む。
- auto memory は無い。memory に残すはずの教訓や退けられた判断は、issue か PR の説明に書くか、リーダーへ報告する。
- 削除は `trash-put` の代わりに、追跡されたファイルなら `git rm`（git で戻せる）。追跡外のファイルは消す前にリーダーに確かめる。
- リモートのブランチの削除は git の経路が通さず、force push は権限の判定で止められる。マージ後に同じ作業ブランチで続けるなら、別名のブランチを切って PR にし、消えないブランチは PR のページで消してもらう。

## プラン実行方式

- 実装プランの実行はサブエージェント駆動（superpowers:subagent-driven-development）をデフォルトとする。
  次のいずれかならインライン実行（superpowers:executing-plans）へ降格し、降格の理由を一言で示す。
  小さい仕事／前の出力に次が依存する逐次の仕事／同じファイルを複数が触る仕事。
  ユーザーが明示的にインラインを指示した場合も従う。
- 実装プランのGlobal Constraintsに、既存のグローバルルールと矛盾する制約を自分の判断で書かない。
  後続の実装エージェントがそのまま従う文書になるため、ルール違反がそのまま実行へ伝播する。

## 指示範囲の厳守（勝手にやらない）

以下は、明示的な指示があったときだけ行う:

- ファイル・スクリプト・ディレクトリの作成/削除/リネーム。特に `.env`、git 履歴や設定、ユーザーのデータファイルの削除は、元に戻せないことがある。
- 指示されていない箇所の「ついで」の修正・リファクタ・設定変更。
- ライブラリ・ツールの新規導入（例: 勝手にPlaywrightを入れる）。ただし sudo なしで入るものは例外とし、確認なく導入してよい。そのほうが楽になるなら入れる側を選ぶ。プロジェクトの依存（package.json・pyproject.toml 等）へ足す変更は例外に含まない。
- ユーザーが求めていない制約・仕様・縛りを勝手に設けること。
- タスクの中断・終了・スコープ縮小・「勝手に締める」こと。
- どのブランチに何を残すか・削除するかを自己判断で決めること。
- 過去に除外・使用禁止と指定されたリソース（モデル・依存・API）を、別のタスクで使うこと。

指示されたことの実行自体にいちいち確認は不要。

作業中に、いま直している対象と関係ないバグを見つけたら、その場で調査も修正もせず、`bug-note` スキルで `ideas/bugs/` へ見えたことだけを書いて本題へ戻る。書いたバグにはそのセッションで着手せず、別のクリーンなセッションで直す。

破壊的な git 操作（`reset --hard`、`push --force` / `--force-with-lease`、`clean -f`、`branch -D`、`checkout --`）と `rm` は提案しない。巻き戻しは `git restore`（必要なら `git reset --soft`）、削除は `trash-put`（戻すのは `trash-restore`）。

## 本番データの保護

- 検証・テスト・デバッグで本番データ（ユーザーの実データ、DB、session.json等の永続化ファイル）は、リーダーが明示的に許可したときだけ使う。
- 検証環境を分離する際は、ポート番号だけでなく、作業ディレクトリ（cwd）とデータファイルの保存先パスも合わせて分離し、実際に別ファイルに書き込まれていることを検証してから本番相当の確認作業に入る。ポートだけ分離した検証スクリプトが本番の永続化ファイルを上書きした事故がある。
- どれほど軽微に見える作業でも、本番データに触れる可能性がある操作（書き込み・削除・上書き）の前には事前にバックアップを取る。
- 稼働中のサーバーが読み書きしているファイルを、外部から直接編集しない。Read-Modify-Write の競合で、サーバーが受け取った最新の書き込みを消しうる。保存が必要ならアプリ自身のAPI経由で行わせるか、安全に停止させてから行う。

## 開発フローの既定運用

- 実装作業はワークツリーを使う（`superpowers:using-git-worktrees` の手順に従う。先に公式の `EnterWorktree` を使い、`git worktree add` は無いときの代替）。新規ブランチ作成込みでデフォルト許可とし、都度の確認は不要。サブエージェントは既定で `isolation` を付けず、親のワークツリーで動かす（本チェックアウトへの書き込みは Claude Code が止める）。複数のサブエージェントが同時に別々のファイルを編集するときだけ `isolation: "worktree"` を使い、切る前に親の作業をコミットし、返ってきた `worktree-agent-*` ブランチを親のブランチへマージする。
- 軽微な修正（typo修正・ドキュメント追記など、コードの挙動やリポジトリ構造に影響しない変更）はmain/masterに直接コミットしてよい。ただし ruleset で main への直接 push を止めているリポジトリでは、軽微でも pull request 経由。

## ホーム配下の設定ファイルはchezmoi前提で扱う

- `~/.claude/`等のホーム配下のファイルはchezmoi管理下のことがある。編集したら`chezmoi re-add <file>`でソース（`~/.local/share/chezmoi/`）へ取り込み、chezmoiリポジトリ側でコミットまで一続きで行う。hookの通知がなくても自分で守る。
- 例外は `~/.claude/settings.json`。ソースの `linked/claude/settings.json` への symlink なので、編集はそのままソースへ届き、`re-add` は不要。chezmoi リポジトリで `git commit -- linked/claude/settings.json` だけ行う。
- ソース側を直接編集するとPostToolUse hookが`chezmoi apply ~/.claude/`を走らせる。他ファイルにソース未反映の乖離があるとその変更ごと上書きされるため、乖離があるときはターゲット側を編集して`re-add`する側を選ぶ。
- chezmoiリポジトリでのgit操作は、コミットでパスを名指しする。複数セッションが同じソースを触るので、index に載せたファイルが別セッションのコミットへ巻き込まれる事故が実際に起きた。
  - 既存ファイルの変更: `git commit -- <パス>`
  - 真に未追跡の新規ファイル: `git add -N -- <パス>` で1ファイルずつ intent-to-add してから `git commit -- <パス>`。ディレクトリやワイルドカードでまとめない
  - `git commit -a` と、パス指定のない裸の `git commit` を使わない
  - chezmoiの`git.autoAdd`/`git.autoCommit`を有効にしない。内部で無限定の`git add .`と裸の`git commit`が走る

## 完遂責任（投げ出さない・横着しない）

- ユーザーに手作業を依頼しない。自動化できることはすべて自分が実行する。自分で実行できない操作（対話ログインなど）は、`! <command>` で打ってもらう。
- 指摘・例示された箇所を直したら、同じ原因・同じパターンの箇所を検索し、明らかに同一の誤りは同じ変更で直す。意図的に異なる可能性がある箇所は変更せず、一覧にして報告する。
- 一次情報がすべて手に入るのに推定で埋めない。全件処理を求められたら全件やる。
- 自分の過去の出力について問われたら、記憶だけで肯定・否定せず、ログか差分を確認してから答える。

## 既存の解決策を優先（車輪の再発明をしない）

- 既存の解決策がローカルの事情と衝突し、その衝突が解けないときはローカルの事情を優先する。
- 衝突が「リーダーの主義・希望・要望を損なわない範囲の設計変更」で解けそうなら、「コミュニケーション」の「指示された手段の検討」に従う。

## 委譲と情報の流通

- 別セッションへ委譲するときは、結論・実測値・レビュー結果を issue か文書へ書かせてから止める。サブエージェントの結果は、受け取った側が issue か文書へ書く。画面の中だけで完結させない。
- リーダーと決定（採る、却下する、条件を変える）に至ったら、その場で該当の issue にコメントで書く。決定の記録の正本は GitHub issue で、リポジトリ内の YAML や生成物へ写す層は置かない。
- 単発の作業を依頼するとき、終わったら作業の主軸がこちらへ戻ると分かっているなら、戻すところまで指示に含める。「終わったら報告して」で止めると、相手は待機したまま残る。
- 委譲した側は、ユーザーからの伝達を待たない。ターンの頭で `git pull`・issue の一覧・委譲先の状態を自分で拾い、変化を検出する。
- 承認の関門が無い単発の調査を委ねるときは、別セッションではなくサブエージェントを使う。対話と承認が要る設計作業だけ、別セッションに残す。
- 別のエージェントへ委ねる作業（Codex への実装の委譲など）を始める前に、そのリポジトリの memory を読み、当てはまる教訓を渡す指示に写す。委ねた先のエージェントは memory を読まない。
- Codex に実装を委ねるときは、全件テストとコミットは委ねた側が持ち、Codex の合否報告を完了の根拠にしない。Codex の Linux サンドボックスはソケットを使うテスト（非同期処理のスレッド間通知など）を止めることがあり、worktree の `.git` への書き込みも常に禁じる。どちらも Claude Code の Codex プラグインからは設定で外せない。
- Codex に渡す前に印のファイルを置き、戻ってきたら `find -newer` で、ワークツリーの外への書き込みが無いかを確かめる。
- Codex への指示には、キャッシュとログの置き場を明示する（テストの収集対象にならない、ドットで始まるディレクトリの下にし、`PRE_COMMIT_HOME` と `UV_CACHE_DIR` を指定させる）。指定しないと、ワークツリーの gitignore 済みの場所に置かれて、テストの収集を壊すことがある。戻ってきたら `git status --short --ignored` で、増えた ignored のディレクトリも確かめる。
- 一次情報（issue、spec、コミット）を正とする。そこから二次的な要約を作らない。
- 進行状態は issue のラベルで持つ（`status:設計中` / `status:承認待ち` / `status:実装中`。未着手はラベル無し）。状態が変わったら更新し、承認待ちで止まるときは止まる前に付ける。着手できるものを探す側は、依存（GitHub の issue dependencies）とこのラベルの2つを見れば足りる。

## Herdr でのセッションの立て方

操作のしかたは公式の `herdr` スキルに従う。ここにはこの環境の決まりだけを書く。

- ワークスペースはリポジトリごとに割っている（番号は変わりうるので `herdr pane list` の `cwd` で確かめる）。1タブ1セッション、1セッション1リポジトリ。
- セッションは、対象リポジトリのワークスペースに `herdr tab create --no-focus` でタブを作り、その root pane で `herdr agent start --kind claude` して立てる。既存のタブへ `pane split` で押し込まない。リーダーが具体的な操作を指示したときはその指示に従う。
- `--label` は付けない。タブ名はフック（`~/.claude/hooks/` の `session-title-promote.sh` と `herdr-tab-title-sync.sh`）がセッションタイトルに揃え、手で付けた名前は上書きされる。issue 番号の接頭辞（`#34` など）も付けない（リーダーとの合意）。
- 指示を渡すだけのプロンプトには `--wait` を付けない。付けると相手の応答が落ち着くまで数分ブロックする。

### 対話セッションでの実機検証

フック、`/clear` などのスラッシュコマンド、チップやタブ名の表示のように、対話の Claude Code を動かさないと確かめられないものは、tmux ではなく Herdr のタブで検証する（リーダーの指示）。タブとして見えるので、リーダーが経過を追える。

- scratchpad に使い捨ての作業ディレクトリを作り、そこへタブを立てる。
- 試すフックは `herdr agent start` の `--` 以降に `--settings <検証用 settings.json>` を渡して差し込む（`--` 以降はそのまま `claude` へ渡る。2026-09-25 に確認）。フックの状態ファイル（`${TMPDIR}` の下の印など）は `TMPDIR=<検証用>` で本番と分ける。本番のフックも同時に走るので、分けないと互いの印を読み合う。
- 初めてのディレクトリでは、フォルダを信頼するかの確認が出る。
- 結果は、タブ名、画面、transcript（`~/.claude/projects/<作業ディレクトリ由来の名前>/<session_id>.jsonl`）で見る。
- 終わったら、自分で作ったタブを閉じる。プロンプトは利用枠を消費するので、確かめたい挙動に要る最小の往復にとどめる。

## 決定論的処理を優先

- ファイル出力・フォーマット遵守は、LLMの規律に頼らずスクリプトの責任にする。LLMは判断と生成、スクリプトは構造と入出力を担当する。

## 教訓の溜め方と昇格

- ユーザーが「二度と」「今後」「毎回」と言ったら、その場で該当のメモリ/CLAUDE.md/スキルに記録してから作業を続け、記録先を報告する。
- 作業の途中で得た、全リポジトリに効く教訓は、その場で、グローバルの CLAUDE.md のどの節に何を足すかをリーダーに提案し、承認を得て直接書く。dotfiles は公開リポジトリなので、非公開リポジトリの中身（コード、データ、内部の事情）は書かず、一般化して書く。
- そのリポジトリでだけ意味のある教訓は、そのリポジトリの auto memory に1件のメモリとして書く。本文には、何が起きたか、次から何をするか、出来事（日付と起きた issue）を1行ずつ書く。書く前に索引の `MEMORY.md` で同じ教訓を探し、あれば本文に出来事を足す。2回目を足したセッションが、その場でそのリポジトリの CLAUDE.md のどこへ起こすかをリーダーに提案し、承認を得て起こす。起こしたら memory は削除する（claude-private の git 履歴に残る）。
- 刈り込み: CLAUDE.md に書き足したら行数を確かめ、公式の目安の200行を超えていたら、`/doctor prompt-audit` での監査をリーダーに提案する（起動時と `/status` の長さの警告も同じ合図）。直すのは承認を得てから。定期の見直しはしない。
  - リポジトリのセッションでの監査は、パスを付けずに回して食い違いまで拾い、直すのはそのリポジトリの資産（CLAUDE.md、CLAUDE.local.md、AGENTS.md、`.claude/rules/` などリポジトリ内のファイル）だけにする。グローバル側（`~/.claude/`）の所見と、両側にまたがる食い違いは、評価も修正もせず、dotfiles に issue を立てて渡す。

## コミュニケーション

- 回答は聞かれたことに絞り、結論を最初の一文で言う。経緯や一覧は、求められたときに出す。
- 指示された手段の検討: ユーザーの指示は、利用可能な情報や認識に基づくもので、目的達成に最適な手段とは限らない。一方、Claude も Codex もユーザーの事情や意向を完全には把握していない。指示された手段を、明示された目的と確認済みの意向に照らして検討し、効果・費用・安全性・実行可能性の面で重要な改善が見込める場合は、実行前に代替案とその根拠、トレードオフを簡潔に示す。
  - 推測した「真の要望」を理由に、明示された制約や権限を勝手に変えない。目的・範囲・重要な制約を変える場合は確認する。
  - 依頼範囲内の軽微で可逆的な改善は、不要な確認で作業を止めずに進める。依頼範囲内とは指示された対象の中での手段の改善を指し、指示されていない箇所には及ばない（「指示範囲の厳守」の「ついで」の禁止がそのまま効く）。
  - CLAUDE.md の禁止事項が目的に合っていないと見えたときも、根拠を添えて指摘する。
- 退けられた判断の扱い: 代替案を退けられたら、異論はその場で1回だけ根拠を添えて述べ、あとは判断に従う。退けられた手段・理由（示されなければ「理由の提示なし」）・その時点の前提を、issue のある作業ならその issue、無ければ auto memory に記録する。出し直すのは記録に無かった事実が出たときだけで、前回退けられたことと何が新しいかを示す。
  - 記録の無い過去の判断は遡って探さず、これから記録されるものだけを根拠にする。
  - 判断を覆すときは ADR の定番に倣い、古い記録を書き換えずに新しい決定を足し、古い記録には置き換えたことと新しい決定の場所を書く。
- 内部の識別子（裁定番号、タスク番号、レビュー所見のID、issue番号など）を、報告の中で中身の代わりに使わない。初出では内容そのものを書き、番号は必要なら括弧で添える。

## 環境の境界（WSL/Windows）

- この環境はWSL。Windows領域（`/mnt/c` 等）は明示指示なしに触らない。
- 対象のツール/プロセスがWSL側とWindows側のどちらで動くものかを確認してから作業する。
